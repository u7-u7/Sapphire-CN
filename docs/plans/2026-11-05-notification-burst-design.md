# 通知及时性与连续消息修复

用户已确认：同一应用的新消息直接刷新当前弹窗并重新计时，不再逐条排队。

复现结果：队首固定占用 15 秒；相同 record ID 会被队列忽略；游标只比较 ID 和投递时间，无法识别同一记录的正文变化。文件监听每次触发都销毁重建，漏事件需等待 5 秒轮询。通知展示还共享其他活动的 debounce 和后台限速。

实现计划：

1. 队列按应用合并，当前应用即时更新，其他应用各保留一条最新消息并保留先后顺序。普通弹窗 6 秒；有其他应用等待时限制同一应用连续占用，避免消息洪峰饿死其他应用。
2. 游标比较解析后的正文及投递时间，同一记录的内容变化可再次投递。展示使用独立版本身份，旧关闭回调不能关闭新版本；无正文变化不重复弹出。
3. 保留健康的数据库、WAL 和目录监听，只在文件替换后重建；事件合并缩短到 50ms，兜底检查为 1 秒。新通知通过独立展示订阅，不与普通活动 debounce 或后台节流一起等待。
4. 保留前台应用抑制。iMessage 正在输入回复时保护当前消息和接收人，暂存最新消息，结束输入后刷新；计时器不在输入期间关闭弹窗。
5. 扩展现有离线回归，覆盖突发消息、同记录正文更新、元数据重复、版本身份、跨应用顺序和旧回调；完整构建后进行本机验证。修复先在本地验证，未自动发新版本。

数据库通知落盘时间由 macOS 决定；减少应用自身等待，不承诺与原生横幅零延迟同步。`writing-plans` 技能在当前安装目录不可用，此文件保留明确的实现步骤及验证边界。
