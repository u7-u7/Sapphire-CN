# Sapphire-CN 自有 GitHub 应用内更新方案

状态：用户已确认直接实现、实测并发布换源版。范围限主应用的更新检查、下载、版本识别及发行包，不修改第三方应用更新器或 Helper 协议。

## 现状证据

- `Sapphire/App Settings/UpdateChecker.swift` 的 API 和发行说明回退 URL 指向 `cshariq/Sapphire`；首次引导的下载链接同样指向上游。
- 已发 CN1–CN3 都是预发布，包内版本均为 3.0 (1)。稳定通道会排除预发布，标签 3.0-cn.3-preview 排序又低于营销版本 3.0。
- 安装器要求标签版本与包内版本对应；Helper 要求营销版本或 build 递增。保持既有校验，不能只改 URL 或强行放宽版本检查。
- 当前安装 ZIP 包含指向 /Applications 的绝对软链接，会被已有归档检查拒绝。

## 推荐方案

1. 发布 `v3.0-cn.4-preview` 换源版；系统营销版本继续 3.0，主应用 build 递增至 4，Info 新增 `SapphireCNReleaseVersion=3.0-cn.4-preview`。
2. 主更新器统一读取 `u7-u7/Sapphire-CN`，仅选择 CN 标签，包含本仓库的公开预发布；界面明确显示 CN 开发预览通道，不使用上游付费 Beta 选择规则。
3. 使用独立 CN 发行标识比较/显示/核对候选版本，保留原营销版本传给安装阶段及旧 Helper；Helper 无需升级协议。公开构建的主进程签名接口是占位实现，更新安装边界须复用 Helper 的真实系统验签规则。
4. CN 缓存、ETag、持久化可用更新和检查调度独立命名，不恢复上游下载候选。
5. 发布仅包含完整 `Sapphire.app` 的独立 `-update.zip` 用于应用内更新，保留手动安装 DMG/ZIP；更新器优先选 update.zip，保留摘要、大小、路径、架构和同团队签名校验。
6. 首次启动和 About 下载/发行说明统一指向本仓库，保留上游作者署名。

## 首次迁移限制

已发旧程序硬编码上游地址，无法仅靠本仓库发布更新远程改写。CN1–CN3 用户需先手动安装一次换源版，此后可在应用内持续检测和下载 CN 更新。不能把旧版宣称为已自动切源。

## 验收与交付

不新增测试用例。使用真实 GitHub release、实际更新 ZIP、已构建签名应用验证检查/下载/摘要/包体，检查同版不重复提示；在隔离副本验证升级流程，避免用构造返回冒充真实网络验收。发布前保留原应用和设置，验证后恢复配置。发布包继续标为未公证 arm64 开发预览。
